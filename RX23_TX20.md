### 🔄 Pairing Process (Work in Progress)

*The exact pairing protocol is still under investigation, but preliminary observations suggest the following sequence:*

* **Remote pairing mode**
  When entering pairing mode, the remote transmits on a slightly different channel (\~2.44 GHz) at a noticeably slower burst rate.

  ```
  c710f55cccccca518cbb4a850
  ```

* **Car response** (confirmed via HackRF)
  The car appears to respond on \~2.405 GHz using a similar burst format:

  ```
  c710f55cccccc5aa562df3b2950
  ```

* **Pairing completion**
  The remote's LED indicates a successful pair. Immediately after this, the remote begins transmitting on the **normal data channel** (\~2.444 GHz), using a valid “speed” control packet:

  ```
  c710f55fb46a5ae04900250
  ```

#### 🧠 `OP` Byte — Bit Layout and Meaning

The **`OP` (OPCODE) field** is **1 byte wide (8 bits)** and encodes two key pieces of information:

#### **Bit layout:**

```
OPCODE: [ d3 d2 d1 d0 | s3 s2 s1 s0 ]
          direction     speed flags
```

| Bits     | Purpose              | Notes                                                                                                         |
| -------- | -------------------- | ------------------------------------------------------------------------------------------------------------- |
| `d3..d0` | **Direction mask**   | Bitmask: `0x1=LEFT`, `0x2=RIGHT`, `0x4=FORWARD`, `0x8=BACK`; combos additive                                  |
| `s3..s0` | **Speed tier flags** | Likely redundant bits derived from speed                                                                      |
|          |                      | - `0x8` = Speed 1  (`1000`)<br> - `0x4` = Speed 2  (`0100`)<br> - `0xC` = Speed 3|

| Direction Combo     | Direction Mask | Bitwise OR | Resulting OP High Nibble |       |
| ------------------- | -------------- | ---------- | ------------------------ | ----- |
| LEFT                | `0x1`          | —          | `0x1`                    |       |
| RIGHT               | `0x2`          | —          | `0x2`                    |       |
| FORWARD             | `0x4`          | —          | `0x4`                    |       |
| BACK                | `0x8`          | —          | `0x8`                    |       |
| **LEFT + FORWARD**  | `0x1           | 0x4`       | `0x5`                    | `0x5` |
| **RIGHT + FORWARD** | `0x2           | 0x4`       | `0x6`                    | `0x6` |
| **LEFT + BACK**     | `0x1           | 0x8`       | `0x9`                    | `0x9` |
| **RIGHT + BACK**    | `0x2           | 0x8`       | `0xA`                    | `0xA` |


#### 🧩 `CMD` Byte — Bit Layout and Meaning

The **`CMD` field** is 1 byte wide (`8 bits`) and encodes **speed** and **steering** information:

```
CMD[7..0] =  b7 b6    b5  b4  b3  b2  b1   b0
              ^  ^    \_____DIR_SIG____/   ^
              ?  ?                         ?
```

| Direction / Combo | DIR_SIGNATURE (b5..b1) | Mask (hex) |
| ----------------- | ---------------------- | ---------- |
| LEFT              | `00001`                | `0x02`     |
| RIGHT             | `11010`                | `0x34`     |
| FORWARD           | `01100`                | `0x18`     |
| BACKWARD          | `00000`                | `0x00`     |
| LEFT + FORWARD    | `00101`                | `0x0A`     |
| RIGHT + FORWARD   | `11110`                | `0x3C`     |
| LEFT + BACK       | `01001`                | `0x12`     |
| RIGHT + BACK      | `10010`                | `0x22`     |

  
### 📡 Packet (“burst”) cadence 
- **While the button is held:** the remote transmits the **drive command** packet repeatedly at ~**83 packets/s** (≈ **12 ms** start-to-start).
- **On release:** the payload **immediately switches to `PARK/NEUTRAL`**, but the remote **keeps transmitting at the same cadence** for a built-in **post-release dwell**, so a “short press” still shows ~**100 packets** in URH.

What that means in practice:

- The car **starts moving** as soon as it receives the first valid *drive* packet.
- The car **stops** shortly **after the last drive packet**, either because it receives *PARK* packets or because its internal **watchdog** (~0.1 s typical) expires.  
  The extra packets you see after release are mostly **PARK** and **don’t keep it moving**—they just ensure the stop command is delivered reliably.

time ──▶ [drive][drive][drive]........(release)→[PARK][PARK]...[PARK]

* **One line in URH = one packet (a.k.a. frame/burst).**
  A short press produced **\~102 packets over \~1.22 s** ⇒ **\~83 packets/s**.
* **Packet length (on-air):** \~**213 bits** ≈ **1700–1800 samples** at 2 MS/s, SPS = 8 → **\~0.85–0.90 ms**.
* **Symbol timing:** SPS = 8 @ 2 MS/s → **4 µs per symbol** (≈ 250 kb/s).
* **Start-to-start interval:** \~**11.9 ms**.
  **Inter-packet gap (silence):** \~**11.0–11.2 ms** (you see `Pause: ~22k samples` in URH).

> **Long press:** packets continue at \~**83 Hz** until release.
