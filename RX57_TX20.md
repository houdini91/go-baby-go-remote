### 🔄 Pairing Process (Work in Progress)

*The exact pairing protocol is still under investigation, but preliminary observations suggest the following sequence:*

* **Remote pairing mode**
  When entering pairing mode, the remote transmits on a slightly different channel (\~2.44 GHz) at a noticeably slower burst rate.

  ```
  c710f55cccccca518cbb4a850
  ```

* **Car response** (confirmed via HackRF)
  The car appears to respond on \~2.405 GHz using a similar burst format:

  ```
  c710f55cccccc5ae6f0bd4db950
  ```

* **Pairing completion**
  The remote's LED indicates a successful pair. Immediately after this, the remote begins transmitting on the **normal data channel** (\~2.446 GHz), using a valid “speed” control packet:

  ```
  c710f55bd0f67aa08581f50
  ```

#### 🧠 `OP` Byte — Bit Layout and Meaning

The **`OP` (OPCODE) field** is **1 byte wide (8 bits)** and encodes two key pieces of information:

```
OPCODE: [ d3 d2 d1 d0 | s3 s2 s1 s0 ]
          direction     speed flags
```

| Bits (MSB→LSB)        | Purpose            | Notes                                                                                                                                              |
| --------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **b7..b4 (`d3..d0`)** | **Direction mask** | Bitmask (additive): `0x1=LEFT`, `0x2=RIGHT`, `0x4=FORWARD`, `0x8=BACK` → e.g., `0x5=LEFT+FWD`, `0x6=RIGHT+FWD`, `0x9=LEFT+BACK`, `0xA=RIGHT+BACK`. |
| **b3..b0 (`s3..s0`)** | **Speed nibble**   | RX57 mapping: **S1 = `0x8` (`1000`)**, **S2 = `0x4` (`0100`)**, **S3 = `0xC` (`1100` = `S1 \| S2`)**.                                              |


| Direction Combo | Direction Mask (hex) | Bitwise OR         | Resulting OP High Nibble | Example OP (S1 / S2 / S3) |
| --------------- | -------------------- | ------------------ | ------------------------ | ------------------------- |
| LEFT            | `0x1`                | —                  | `0x1`                    | `0x18 / 0x14 / 0x1C`      |
| RIGHT           | `0x2`                | —                  | `0x2`                    | `0x28 / 0x24 / 0x2C`      |
| FORWARD         | `0x4`                | —                  | `0x4`                    | `0x48 / 0x44 / 0x4C`      |
| BACK            | `0x8`                | —                  | `0x8`                    | `0x88 / 0x84 / 0x8C`      |
| LEFT + FORWARD  | `0x1`, `0x4`         | `0x1 \| 0x4 = 0x5` | `0x5`                    | `0x58 / 0x54 / 0x5C`      |
| RIGHT + FORWARD | `0x2`, `0x4`         | `0x2 \| 0x4 = 0x6` | `0x6`                    | `0x68 / 0x64 / 0x6C`      |
| LEFT + BACK     | `0x1`, `0x8`         | `0x1 \| 0x8 = 0x9` | `0x9`                    | `0x98 / 0x94 / 0x9C`      |
| RIGHT + BACK    | `0x2`, `0x8`         | `0x2 \| 0x8 = 0xA` | `0xA`                    | `0xA8 / 0xA4 / 0xAC`      |


#### 🧩 `CMD` Byte — Bit Layout and Meaning

The **`CMD` field** is 1 byte wide (`8 bits`) and encodes **speed** and **steering** information:

```
CMD[7..0] =  b7 b6    b5  b4  b3  b2  b1   b0
              ^  ^    \_____DIR_SIG____/   ^
              ?  ?                         ?
```

| Direction / Combo | DIR_SIGNATURE (b5..b1) | Mask (hex) |
| ----------------- | ---------------------- | ---------- |
| LEFT              | `00101`                | `0x0A`     |
| RIGHT             | `11110`                | `0x3C`     |
| FORWARD           | `01000`                | `0x10`     |
| BACKWARD          | `00100`                | `0x08`     |
| LEFT + FORWARD    | `00001`                | `0x02`     |
| RIGHT + FORWARD   | `11010`                | `0x34`     |
| LEFT + BACK       | `01101`                | `0x1A`     |
| RIGHT + BACK      | `10110`                | `0x2C`     |

### 📡 Packet (“burst”) cadence — RX57

* **While the button is held:** the remote transmits the **drive command** packet repeatedly at ~**82.7 packets/s** (≈ **12.09 ms** start-to-start).
* **On release:** the payload **immediately switches to `PARK/NEUTRAL`**, but the remote **keeps transmitting at the same cadence** for a short **post-release dwell**, so a “short press” still shows a sizeable burst in URH.

What that means in practice:

* The car **starts moving** as soon as it receives the first valid *drive* packet.
* The car **stops** shortly **after the last drive packet**, either because it receives *PARK* packets or because its internal **watchdog** (~0.1 s typical) expires.
  The extra packets you see after release are mostly **PARK** and **don’t keep it moving**—they just ensure the stop command is delivered reliably.

time ──▶ [drive][drive][drive]........(release)→[PARK][PARK]...[PARK]

* **One line in URH = one packet (a.k.a. frame/burst).**
  A short press produced **~1.15 s** of activity → **~95 packets** at **~82.7 packets/s**.
* **Packet length (on-air):** **~0.864 ms** = **216 symbols** at SPS = 8 & 2 MS/s → **4 µs/symbol** (≈ 250 kb/s).
* **Start-to-start interval:** **~12.09 ms**.
  **Inter-packet gap (silence):** **~11.15 ms** (by direct measure); computed from start-to-start minus on-air is **~11.23 ms** (minor rounding difference is expected).

> **Long press:** packets continue at **~82.7 Hz** until release.
